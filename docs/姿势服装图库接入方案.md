# 姿势 / 服装图库接入方案（sd-cli 路线）

> 需求来源：用户看中开源项目 **comfyui-aicg3d-PoseSwap**（`D:\Comfy-Desktop\Comfyui-OpenFrame\comfyui-aicg3d-PoseSwap-main`），
> 希望把「选姿势 → 换姿势 → 换服装」搬进 LocalGen。
> 决策：**走 sd-cli（方案 C）**，不把该插件装进 ComfyUI。
> 本文先给结论与取舍，确认后再动代码。

---

## 1. 那个项目是什么

一个 **ComfyUI 自定义节点包**（MIT，作者 JGRFW），两个能力：

| 能力 | 引擎 | 它是怎么实现的 |
| --- | --- | --- |
| 换姿势 | Qwen-Image-2.1 + 姿势 LoRA | `TextEncodeQwenImage21` → LoRA → Cache → KSampler |
| 换服装 | Qwen-Image-Edit-2511 + Lightning 4 步 LoRA | `TextEncodeQwenImageEditPlus(image1=人物, image2=服装)` |

外加三套本地图库，这是它最值钱的部分：

| 图库 | 规模 | 索引 | 内容 |
| --- | --- | --- | --- |
| `library/` 姿势 | 1439 条（原图+缩略图，2884 文件 / 119.6 MB） | `data/pose-zh.json` | 四个体系（全身性感系/全身标准系/上半身单人/双人缠绵），每条带分类、姿势名、正面·俯视·侧面等多角度 |
| `garments/` 服装 | 1410 文件 / 113.7 MB | `data/garment.json` (235 KB) | 服装套装参考图 + 款式描述 |
| `portraits/` 人像 | 3003 文件 / 148.3 MB | `portraits/data/` | 1499 张 768×960 WebP + 360×450 缩略图 |

姿势索引的字段结构（已实测）：

```json
{"id": "full_sexy_P001_front", "体系": "全身单人・性感系", "姿势编号": "P001",
 "分类": "站姿", "姿势名称": "S形站姿・胯部侧顶", "角度": "正面",
 "缩略图": "thumbs/full_sexy_P001_front.jpg",
 "原图": "img/full_sexy_P001_front.webp",
 "检索": "full_sexy_P001_front 全身单人・性感系站姿S形站姿・胯部侧顶正面"}
```

同一 `姿势编号` 有多个 `角度`，选姿势时应当**按编号聚合、让用户挑角度**，这是原插件的交互，值得照搬。

## 2. 为什么不能直接把插件装进 ComfyUI

两条硬阻断，都是实测出来的，不是推测：

### 2.1 导入即崩

插件 `__init__.py:30`：

```python
from comfy_extras.nodes_qwen import TextEncodeQwenImage21, QwenImage21Cache, TextEncodeQwenImageEditPlus
```

本机 ComfyUI `0.3.76` 的 `comfy_extras/nodes_qwen.py` 只有两个类：

```
nodes_qwen.py:8   class TextEncodeQwenImageEdit
nodes_qwen.py:51  class TextEncodeQwenImageEditPlus
```

`TextEncodeQwenImage21` 与 `QwenImage21Cache` **全仓搜索 0 命中**。这是模块顶层 import，一加载就 `ImportError`，整个节点包起不来。

其余依赖都齐（`ModelSamplingAuraFlow` / `CFGNorm` / `FluxKontextImageScale` / `FluxKontextMultiReferenceLatentMethod` 都在），**只差 Qwen 2.1 这一族**。它要求 ComfyUI 0.43+，本机 0.3.76。

### 2.2 权重要求和本机差一个量级

插件默认要 `diffusion_models/qwen/qwen_image_2.1_bf16.safetensors`（bf16 约 **40 GB**）或 int8 版，加 `qwen3vl_8b_int8_convrot` 编码器和姿势 LoRA。

本机现状：

| 角色 | 本机有什么 | 大小 |
| --- | --- | --- |
| Qwen 2.1 主模型 | `localgen-moss/models/qwen_image_2.1-Q4_K.gguf` | 4003 MB（Q4_K 量化） |
| 编码器 | `Qwen3VL-8B-Instruct-Q4_K_M.gguf` + `mmproj-…-F16.gguf` | 4792 + 1106 MB |
| VAE | `qwen_image_2.1_vae_bf16.safetensors` | 644 MB |
| ComfyUI 侧 | `diffusion_models/` 只有 z-image-turbo；`loras/` 空 | — |

显卡 **RTX 4050 Laptop / 6141 MiB**。本机跑 Qwen 2.1 1024² 文生图实测 **337 s、峰值 5605 MiB**；参考图编辑 **604–835 s**。插件作者在 16 GB 的 5070 Ti 上跑三段链路 80 秒——**我们连一段都吃力，三段串联不现实**。

## 3. 选定路线：sd-cli 直接调

`sd-cli.exe`（stable-diffusion.cpp `0b3b98d`，在 `localgen-moss/bin/`）已实测支持本项目需要的全部能力：

| 需要的能力 | sd-cli 参数 | 状态 |
| --- | --- | --- |
| Qwen-Image-2.1 编辑 | `--diffusion-model` + `--llm` + `--llm_vision` + `--ref-image` | **现在就在用** |
| **多张**参考图 | `--ref-image`（can be used **multiple times**） | ✅ 关键：换姿势需要「人物 + 姿势」两张 |
| LoRA 加载 | `--lora-model-dir` + `--lora-apply-mode auto/immediately/at_runtime` | ✅ 姿势 LoRA 可挂 |
| Qwen 2.1 专用加速 | `--sigmas qwen-image-2.1-turbo`、`--model-args qwen_image_2_1_prefix_cache` | ✅ |
| 6 GB 显存适配 | `--max-vram 6`、`--offload-to-cpu`、`--params-backend`、`--vae-tiling` | ✅ 已有 `--max-vram -1` 用法 |
| 参考图裁剪规则 | `--image-preprocess target=ref,index=N,mode=crop,width=W,height=H` | ✅ 可按张控制 |

**这套东西现在已经在 LocalGen 里跑通了**：`workflows/qwen-image-21/1.0.0` 的模板 `class_type` 是 `LocalGenQwenImage21`（不是真 ComfyUI 节点），`runner = "sdcpp"` 时由 `sdcpp.QwenImageJob` 拼命令行，走 `--ref-image`。

所以方案 C 的本质是：**把 QwenImageJob 从「一张参考图」扩到「人物图 + 姿势图/服装图」，再加一层图库 UI**。不引入新引擎、不下载新权重、不动 ComfyUI。

## 4. 要做的三件事

### 4.1 图库（纯数据，零风险，可先做）

把三套图库从插件目录**拷进** LocalGen 数据目录（约 380 MB）：

```
data/libraries/poses/      img/ + thumbs/ + index.json   (从 pose-zh.json 转)
data/libraries/garments/   img/ + index.json
data/libraries/portraits/  img/ + thumbs/ + index.json
```

- 索引原样保留中文，只补一个统一的 `id` 主键。
- 姿势按 `姿势编号` 聚合，`角度` 做同一卡片的多视角切换。
- 提供 `/api/v1/libraries/{kind}` 列表 + `/api/v1/libraries/{kind}/{id}/image` 出图接口。
- **附带许可信息**：三套图库的 LICENSE / NOTICE 必须一起拷，UI 里能查。

### 4.2 引擎（改 `sdcpp.py`，风险集中在这里）

新增 `PoseSwapJob`（或给 `QwenImageJob` 加 branch），核心差异是**两张参考图**：

```python
# 当前（单参考图）
if ref_image is not None:
    self.command.extend(["--ref-image", str(ref_image), "--llm_vision", vision])

# 目标（人物 + 姿势）
self.command.extend([
    "--ref-image", str(person_ref),     # image_1：人物，保留身份
    "--ref-image", str(pose_ref),       # image_2：姿势，决定动作
    "--llm_vision", vision,
    "--increase-ref-index",             # 按顺序编号，避免两张图混淆
])
```

两张图各自要按输出长宽比预处理，用两条 `--image-preprocess` 分别指定。

**P0 已验证通过（2026-11-09 23:43）**：sd-cli 双 `--ref-image` 确实能区分「定身份」和「定姿势」，见第 8 节实测记录。

### 4.3 界面（复用现有桌面）

- 左栏生成区加「姿势」「服装」两个选择器，点开是图库浏览面板（缩略图瀑布流 + 分类/体系筛选 + 关键词搜索）。
- 选中后显示一张小预览，可清除。
- 复用现有的参考图上传位：**人物图走原来的参考图，姿势/服装走新选择器**。
- 生成记录里记录 `pose_id` / `garment_id`，能追溯。
- 进度条 / 状态条 / ETA 全部沿用现有机制（`Progress` 是 JSON TEXT，加字段不用迁移）。

## 6. 明确不做

- 不升级 ComfyUI 到 0.43（会牵动现有 6 个已验收工作流，风险太大）。
- 不下载 40 GB bf16 权重。
- 不整段复用原插件的 `__init__.py`（49 KB，深度绑定 ComfyUI 节点体系）。
- 不默认搬运 `portraits/` 人像库（它标注 CC0 但**同时请求避免再分发**，用户要用再单独确认）。

## 6.5 图像编辑模型全家桶（用户新增需求）

### 现状盘点

LocalGen 现有 7 个工作流，按「能不能编辑」分类：

| 工作流 | 引擎 | 类型 | 权重 | 编辑质量 |
| --- | --- | --- | --- | --- |
| `qwen-image-21` | sdcpp | **编辑 + t2i** | 4003 + 4795 + 1105 + 644 MB | **最好**（P0 实测姿势跟随+身份保留都成立） |
| `kontext-dev` | sdcpp | **编辑专属** | 6611 + 235 + 2612 + 320 MB | 待实测，FLUX Kontext 是成熟编辑模型 |
| `moss-image` | moss | t2i + **图生图（勉强可用）** | 3173 MB | 用户判断"勉强可用"，作备选 |
| `z-image-turbo` | comfy | t2i | GGUF 缺失 | 不作编辑用途 |
| `sd15` / `sdxl-lightning` | comfy | t2i | — | 不作编辑用途 |
| `baseline` | — | 演示 | — | — |

**结论：编辑模型三个 —— `qwen-image-21`（主力）、`kontext-dev`（待测）、`moss-image`（备选）。**

用户确认："moss-ige 图生图也勉强可以用"。moss 的 `MossJob` 本来就有 `init_image` 通道（`moss.py:38` 调 `stage_reference`），所以它接进统一编辑接口**不需要改引擎**，只是要在 `capability` 里标成可编辑、并在 `engine: auto` 的分派表里排第三。

用户还说"我是不是还有另外一个图像编辑的模型"——指的就是 `kontext-dev`。它现在已在库里，但和文生图混在一起、界面上没区分，用户感觉不到它是个编辑模型。


### 要做的：把「编辑」变成一等公民

不是加新模型，而是**把已有能力重新组织成用户能一眼看懂的形式**。

#### 6.5.1 工作流分类（后端）

`manifest.toml` 加一个 `capability` 字段，取值：

| 值 | 含义 | 界面表现 |
| --- | --- | --- |
| `generate` | 纯文生图 | 不需要参考图 |
| `edit` | 图生图 / 编辑 | **必须**参考图 |
| `pose` | 换姿势（新增） | 必须人物图 + 姿势图 |
| `garment` | 换服装（新增） | 必须人物图 + 服装图 |
| `demo` | 演示 | — |

这样界面可以按能力分组，而不是让用户面对 7 个平铺的名字猜哪个能编辑。

#### 6.5.2 统一编辑接口（用户要的"更方便"）

现在的问题：`qwen-image-21` 和 `kontext-dev` 参数**不一样**（一个要 `llm`+`llm_vision`，一个要 `clip_l`+`t5xxl`+`guidance`），用户切换模型就得重新理解一遍参数。

设计一个**统一的 `/api/v1/edit` 端点**：

```
POST /api/v1/edit
{
  "engine": "qwen" | "kontext" | "auto",
  "image": "<参考图 token>",
  "prompt": "把她的姿势改成站立",
  "pose": "<姿势 id，可选>",
  "garment": "<服装 id，可选>",
  "size": [1024, 1024],
  "steps": 15
}
```

- 只接受「语义参数」，模型差异由后端翻译成各自的命令行。
- `engine: "auto"` 时按任务类型选：纯指令编辑 → kontext；带姿势/多参考图 → qwen。
- 这个端点是**给外部程序（含 MCP、插件）用的稳定契约**，模型换了不用改调用方。

现有 `/api/v1/jobs` 保持不动（向后兼容），`/edit` 是它的友好外壳。

#### 6.5.3 桌面端：一个「编辑」标签页

- 顶部分段控件：**生成 / 编辑**。切到「编辑」时，参考图上传位变成必填并高亮。
- 编辑页里再分：**指令编辑**（一句话改图）/ **换姿势** / **换服装** —— 对应上面的 capability。
- 每个子模式只显示该模式要的参数，不把 steps/cfg/guidance 全砸给用户；高级参数折叠。
- 状态条明确显示引擎名 + 预计耗时（Qwen 编辑约 7–10 分钟，Kontext 待测）。

#### 6.5.4 Kontext 编辑能力实测结论（2026-11-10 00:38）

用同一张人物图 + 同一个提示词，分别跑 Qwen 双参考图与 Kontext 单参考图：

| 模型 | 参考图 | 步数 | 耗时 | 姿势是否改变 | 身份保留 |
| --- | --- | --- | --- | --- | --- |
| **Qwen-Image-2.1** | 人物 + 骨骼姿势图 | 8（turbo） | **253 s** | ✅ 跪坐 → 站姿，完全跟随 | ✅ |
| **FLUX.1 Kontext dev** | 仅人物 | 20 | 377 s | ❌ **仍是跪坐**，只把一只手抬到头顶 | ✅ |

**结论：Kontext 做不了「按参考图换姿势」。** 它是单参考图的指令编辑模型，没有机制知道目标姿势长什么样，只能照着文字改。

因此 `engine: auto` 的分派规则确定为：

| 任务 | 该用哪个 |
| --- | --- |
| 换姿势 / 换服装（有参考图） | **只能 Qwen**（双/三参考图） |
| 纯指令改图（「把头发变红」「加个帽子」） | Qwen 或 Kontext 均可；Kontext 对局部精修更稳，Qwen 上下文更强 |
| 图生图但无姿势要求 | 任选 |

**不把 Kontext 放进 pose-swap 的候选引擎** —— 它跑 377 s 还改不动姿势，放进去只会让用户误以为坏了。

### 6.5.5 加速实测：sigmas 预设 + 8 步（重大收益）

`--sigmas qwen-image-2.1-turbo` 是本机 sd-cli 内置预设，原本以为只有 Turbo 权重能用，**实测常规 Q4_K 权重同样有效**：

| 配置 | 步数 | 耗时 | 相对 20 步 | 画质 |
| --- | --- | --- | --- | --- |
| euler 默认 sigma | 20 | 420.2 s | — | 基准 |
| **euler + turbo 预设** | **8** | **253.0 s** | **−40%** | **肉眼无差别**（姿势跟随、身份、发色、服装全部一致，画面甚至更干净） |

**pose-swap 默认值已改为 8 步 + turbo 预设。** 这直接回答用户「步数不要改多」——不但没加，还降了一半以上。

实现上有两处必须打通，否则 `sigmas` 会被静默丢弃：
1. `parameters()` 补一层：把模板里**未映射给用户**的引擎字段（`sigmas`/`guidance`/`steps` 等）一并带进 values；
2. `render()` 补一层：把这些字段真正写到节点上（原来只按 `spec.inputs` 映射，`sigmas` 落不到图里）。

两条都有测试锁住（`test_engine_fields_reach_the_node`）。

**用户已确认：接受 10 分钟等待；接入全部编辑模型；开始实施。**

| 项 | 决定 |

关键设计：

- 服装有 `thumb` 字段缺失，`thumb()` 自动回退原图，UI 不会空白
- **`guarded()` 拒绝目录联接** —— 实测过：用 `mklink /J` 指图库会被 503 拦住（安全设计，非 bug）

### P5 已完成（方案 B 的超时修复：流式响应）

用户决策 1 选 B（接成 `zcode-image-gen` 的 openai-compat provider，图自动进画廊）。
配置层已就位（`cordis.patch.yml` 里 `openaiCompatBaseURL: http://127.0.0.1:12138/v1`、
`openaiCompatModel: qwen-image-21`），但真机验证撞上硬墙：

```
openai-compat image request failed after 305.1s:
HeadersTimeoutError [UND_ERR_HEADERS_TIMEOUT]
```

**根因**：Node 侧 undici 的 `headersTimeout` 默认 300 秒。LocalGen 的
`/v1/images/generations` 是同步 JSON——生成完才发响应头，而本机生成要
300–700 秒，**必然输掉这场竞态**。（注意报错是 HeadersTimeoutError 而非
AbortError，说明不是插件主动 abort，300 秒上限有救。）

**修复**：`src/localgen/api/openai_compat.py` 新增 `_streamed_job()`——
`StreamingResponse` 让响应头**立刻**发出（满足 headersTimeout），之后每
20 秒发一个 `\n` 心跳（JSON.parse 容忍前导空白，客户端无感知；undici 的
bodyTimeout 每收到数据就重置），结束时输出与原来完全相同的 JSON。

**真机验证（`.runtime/stream_test.py`）**：

```
HEADERS AT 0.06s  status=200 content-type=application/json
body 2,634,689 B in 702.7s, heartbeats=34
GENERATIONS_OK b64=2,634,604 chars
```

702 秒的长任务完整送达。**任何时长的生成都能过了。**

注意：此修复在**源码版**里，用户正在跑的打包版 dist（19:00 编译）还没有，
需要重新打包才生效。





### 结论：**通过。sd-cli 双 `--ref-image` 能区分「定身份」与「定姿势」。**

### 输入

| 角色 | 文件 | 来源 | 尺寸 |
| --- | --- | --- | --- |
| 人物图 | `.runtime/p0/person.png` | LocalGen 历史结果 `fd4f3a8d` | 1024×1024 |

### 命令

```powershell
sd-cli.exe `
  --diffusion-model qwen_image_2.1-Q4_K.gguf `
  --llm Qwen3VL-8B-Instruct-Q4_K_M.gguf `
  --llm_vision mmproj-Qwen3VL-8B-Instruct-F16.gguf `
  --vae qwen_image_2.1_vae_bf16.safetensors `
  --ref-image person.png --ref-image pose.png --increase-ref-index `
  --prompt-file prompt.txt --output out-both.png `
  --width 768 --height 768 --seed 42 --steps 20 --cfg-scale 4 `
  --sampling-method euler --mmap --disable-image-metadata `
  --backend "diffusion=cuda0,te=cpu,vae=cuda0" --max-vram -1 `
  --flash-attn auto --threads 6
```

- **耗时 570.79 s**（20 步，19.88 s/it），采样 420.22 s，解码 2.93 s
- **姿势**：原图跪坐 → 结果站姿、一手扶头、一手叉腰、单腿外展 —— 与骨骼图**完全一致**
- **身份**：深蓝长发、蓝眼、白透上衣 + 白泳裤、二次元厚涂画风 —— **全部保留**

| 项 | 值 | 对比参照 |
| --- | --- | --- |
| 20 步双参考图 | **570.8 s** | 纯 t2i 1024² 30 步 = 337.5 s |
| 每步 | 19.88 s/it | — |
| 显存 | 未 OOM，`--max-vram -1` 自动调度 | 6141 MiB 卡 |

**单次换姿势接近 10 分钟**。这是 6 GB 卡跑 Qwen-Image-2.1 的物理成本，不是配置问题。产品上要考虑：
- 默认步数降到 12–15（插件用 25 步，我们 20 步已够看）
- 采样器可试 `--sigmas qwen-image-2.1-turbo` 预设看能否提速
- 界面上把"预计 8–10 分钟"明确告知，避免用户以为卡死

### 待验证（已完成）

`--ref-image` 顺序调换的对照实验：

| 顺序 | 耗时 | 姿势跟随 | 身份保留 | 文件 |
| --- | --- | --- | --- | --- |
| person → pose | 570.79 s | ✅ 正确 | ✅ 保留 | `out-both.png` (825 977 B) |
| **pose → person** | **415.41 s** | ✅ 正确 | ✅ 保留 | `out-swapped.png` (793 775 B) |

**两条结论：**

1. **语义不随顺序变** —— 模型按内容判断哪张定身份、哪张定姿势，不依赖位置。代码里不必强制顺序，但**仍应固定一种顺序**（便于复现和排错）。
2. **顺序影响速度，差 155 s（27%）** —— 这是意外的性能发现。原因推测：第一张 `--ref-image` 承担 prefix cache 的构建，把骨骼图（信息密度低、token 少）放第一位构建的缓存更省。**默认采用「姿势在前、人物在后」**。

### 一个重要的补充发现

两张图各自的体积差异很大（人物图 1.9 MB / 姿势图 251 KB），且姿势图是**纯线条骨骼图**。以后图库里的姿势图都是这个形态，这对我们是好事：线条图token 少、语义干净、不携带干扰身份的信息。

### 仍未解决的性能问题

即使 415 s 也偏慢。待试的加速手段（P1 阶段做）：

- `--sigmas qwen-image-2.1-turbo` 预设
- 步数 20 → 12（画质需复验）
- `--model-args qwen_image_2_1_prefix_cache` 显式开启前缀缓存
