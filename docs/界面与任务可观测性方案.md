# 界面与任务可观测性改进方案

> 状态：草案 v0.1（待拍板，未开工）
> 范围：desktop 界面 + 任务详情 + 生成进度 + 队列可观测性
> 不涉及：引擎选型、模型接入、打包流程

---

## 0. 这份文档解决什么

三条来自使用的反馈，背后是同一件事 —— **程序做了很多事，但没说给人听**：

1. 历史里「资料太少」，只有提示词和图片。
2. 生成进度条「某次更新时被删除了」。
3. 大窗口下界面空、小窗口下界面挤，历史面板滚动不听话。

结论先说：**第 1 条是"有数据没显示"，第 2 条不是被删除而是取不到数据，第 3 条是两个真 bug + 一处结构性失衡。** 下面每条都给证据、给方案、给成本，最后给分批顺序和验收标准。

## 1. 现状与证据

### 1.1 数据面：已经有的 vs 界面显示的

`Job` 模型（`src/localgen/jobs/models.py:68-79`）已经携带这些字段，数据库里也都在：

| 字段 | 来源 | 含义 | 现在界面显示 |
|---|---|---|---|
| `created_at` | DB | 提交时刻 | ❌ |
| `started_at` | DB | 真正开始跑的瞬间 | ❌ |
| `finished_at` | DB | 结束时刻 | ❌ |
| `workflow_id` + `workflow_revision` | DB | 用了哪个模型、哪个模板版本 | ❌（只显示 job_id 前 8 位） |
| `parameters.prompt` | DB | 提示词 | ✅ |
| `parameters.negative_prompt` | DB | 负面提示词（**已按模板默认值补齐**） | ❌ |
| `parameters.strength` | DB | 重绘强度（仅图生图） | ❌ |
| `parameters.image` | DB | 参考图令牌（有值 = 图生图） | ❌ |
| `parameters.width/height` | DB | 请求尺寸 | ✅ |
| `parameters.seed` | DB | **实际使用的种子**（留空时后端已随机并落库） | ✅ |
| `artifacts[0].width/height` | DB | **实际输出**尺寸（用于和请求值对账） | ❌ |
| `artifacts[0].size_bytes` | DB | 文件大小 | ❌ |
| `progress.stage/current/total` | DB | 进度阶段与步数 | ⚠️ 只喂给一条 6px 无字细条 |
| `error.code/message/retryable` | DB | 失败原因、可否重试 | ⚠️ 只显示 message + code |

**能从耗时里算出来、但现在没人算的：**

- 排队时长 = `started_at - created_at`（有别的任务在跑时可能是几分钟，用户完全看不见）
- 生成时长 = `finished_at - started_at`（Qwen 实测 337 s / 604 s / 835 s，这才是"这个模型能不能用"的关键数据）

**已经落盘、但界面没接出来的文件：**

| 路径 | 内容 | 价值 |
|---|---|---|
| `data/comfy-output/<job_id>/input.png` | 参考图**裁剪到输出比例后**的那一份 | 就是引擎真正看到的图，比原始上传更能解释"为什么它这样改" |
| `data/comfy-output/<job_id>/prompt.txt` / `negative.txt` | 引擎实际收到的文本 | 可与 DB 交叉校验 |
| `data/gateway-input/<token>` | 原始上传文件 | 原图/EXIF 信息 |
| `data/results/<job_id>/<artifact>.png` | 成品 | ✅ 已显示 |

> ⚠️ 顺带的风险：`gateway-input/` 目前**没有任何清理机制**（已积累 21 个文件，单个 4 MB 级）。一旦以后加 TTL，历史里的参考图就永久丢了 —— 正确做法是提交时把参考图**转存为任务附属物**（`data/results/<job_id>/reference.png`），再让 `gateway-input` 可以安全过期。

**确实缺、必须补后端的：**

| 项 | 为什么缺 | 补法 |
|---|---|---|
| 步数 / CFG / 采样器 / 四个模型文件名 | 只存在于不可变的 `workflows/<id>/<semver>/prompt.api.json`，`/api/v1/workflows` 不返回 | workflow 详情接口加 `engine_parameters`（只读，按 `workflow_id + revision` 取） |
| 采样/VAE 耗时分解 | 只在 `logs/sdcpp-<job>.log` 里 | job 上加 `metrics` JSON（需 schema 迁移） |
| 显存/内存峰值 | 从未采集 | 可选，用 `nvidia-smi` 采样后写日志即可，不必入库 |
| 谁提交的（client_id） | 无此概念 | 见 §4.4，会影响 API 契约 |

### 1.2 进度条：不是被删，是被饿死

**证据链（全部可在仓库里复核）：**

1. `git log -S'QProgressBar' -- src/localgen/desktop/__init__.py` 只有一条提交（`9902d28` V1），**代码上从来没有删过它**。控件仍在 `desktop/__init__.py:297-310`。
2. 显示逻辑是 `setRange(0, progress.total or 0)`：`total` 为 `None` 时就是 `(0,0)` 的忙碌态 —— 一条 6px、无文字、无数字的细条，看起来就像"什么都没发生"。
3. 为什么 `total` 一直是 `None`：sd-cli 的输出走的是**文件背书**路径（`engine/comfy.py:336` 传了 `log_file=`），而 `engine/windows.py` 的文件分支原本写死 `self.reader = None`，**`drain()` 线程根本不启动 → `on_line` 从未被调用过**。
4. 后果不止进度条：`QwenImageJob.on_line` / `KontextJob.on_line` / `MossJob.on_line` 里的显存不足判定也一起失效，真实 OOM 时用户拿到的是笼统的 `ENGINE_EXECUTION_FAILED` 而不是 `GPU_OOM`。**三个 sd-cli 工作流全中。**
5. 而 sd-cli 一直在好心输出进度，现成日志里就有：
   ```
   |=>                |  1/30 -  34.12s/it - ETA 16:29
   |===>              |  2/30 -  22.37s/it - ETA 13:10
   ```
   现有正则 `\|\s*(\d+)/(\d+)\b` + `分母 == steps` 的过滤完全能匹配 —— 只差没人把行送进去。

> 补一条背景：走 ComfyUI 的工作流（sd15 / sdxl-lightning / z-image-turbo）进度是好的，靠 WebSocket 事件。**死的只有 sd-cli 这条路，而它正好是 Qwen / MOSS / Kontext 唯一走的路。**

### 1.3 布局实测（离屏渲染三张截图）

| 观测 | 数值 | 判断 |
|---|---|---|
| 预览卡片 | 804 × 372（1220×840 窗口） | 1:2.16 横条，方形图只用了中间一块 |
| 512² 图实际渲染 | 356 × 356 | 高度受限，左右各空 224 px |

## 2. 设计原则

1. **可解释优先**：界面存在的意义是回答"现在在干嘛、上次为什么慢、这次能不能复现"。装饰性改动一律靠后。
2. **只增不减、不新增模态**：不加会打断流程的对话框；详情用面板而不是弹窗；所有新字段对老数据（缺字段）必须降级显示而不是报错。
3. **能力驱动**：显示哪些字段由 workflow 声明的 `supported_parameters` / `inputs` 决定（有 `strength` 才显示重绘强度，有 `image` 才显示参考图），不写死模型名。
4. **同机零成本**：desktop 和引擎在同一台机器上，能直接读文件的（参考图、成品）就不要走 HTTP 再传一遍。

## 3. 方案 A —— 任务详情（回答"资料太少"）

### 3.1 字段清单（按获取难度分三档）

**A1 已有直接显示（改 desktop 一处，零后端改动）**

- 模型：`workflow title + revision`（title 从 `/api/v1/workflows` 的 items 里映射，无需新接口）
- 三个时刻：提交 / 开始 / 结束（本地时区 `MM-DD HH:MM`）
- 两段耗时：`排队 3 s · 生成 337 s`；运行中显示 `已用 3:12`
- 负面提示词（有才显示，超 60 字省略 + tooltip 全文）
- 重绘强度（workflow 支持才显示）
- 参考图令牌前 8 位（有才显示）
- 产物：实际尺寸 + 文件大小（`2.2 MB`）
- 错误：`code · message`（+ 可重试标记）

**A2 已有实体文件，接出来即可**

- 参考图缩略图 96 px（优先 `comfy-output/<job_id>/input.png`，回退 `gateway-input/<token>`），点击开原图
- 一行"裁剪说明"：`1200×800 → 裁剪 1024×1024`（就是 §1.1 的 no-stretch 规则，用户能直观看懂）

**A3 需要补一点后端**

- `engine_parameters`：步数 / CFG / 采样器 / 四个模型文件名（workflow 详情接口只读新增字段）
- `metrics`：`te_ms / sample_ms / vae_ms`（job 表加一列 JSON，需 `user_version` 2 迁移）— **建议放最后，非必需**
- `client_id`：见 §4.4

### 3.2 布局：详情放哪里

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A（推荐）** | 历史卡改成左右两栏：左 = 任务列表，右 = 选中任务详情（横向 splitter，可拖） | 正好吃掉历史卡那条一直空着的横向空间；不动图片区；详情能有 7~8 行 | 历史卡需要更高一点（≥220 px） |
| B | 预览卡下方展开"详情"折叠块 | 改动最小 | 挤占图片高度，与"预览要大"直接冲突 |
| C | 右侧独立详情抽屉 | 空间充裕 | 又多一列，1220 宽下三列都变窄 |

推荐 A，与 §5 的"历史面板太扁"是同一个改动的两面。

### 3.3 动作（比字段更值钱）

| 动作 | 行为 | 备注 |
|---|---|---|
| **复用参数** | 把该条的 prompt / negative / 尺寸 / 种子 / 强度 / 参考图整组回填左栏 | 回填后不自动提交，人可改 |
| **同参重跑** | 用同样参数、换新随机种子再提交一张 | 对比"同 prompt 不同种子"的常用手法 |
| **复制参数 JSON** | 一行 JSON 进剪贴板（含 workflow_id/revision/seed） | 贴给别人复现的最短路径 |
| 复制提示词 | ✅ 已有 | |
| 打开所在文件夹 | `results/<job_id>/` | 比"另存 PNG"更常用 |
| 删除任务 | ✅ 已有 | |

## 4. 方案 B —— 进度与队列（回答"进度条没了"）

### 4.1 根因修复：两条路选一条

| | 方案 B1：日志 tail（推荐） | 方案 B2：管道 + tee |
|---|---|---|
| 做法 | 保留"stdout 写文件"，另起一条线程跟随该文件，把行喂给 `on_line` | 改回管道读取，在 `drain()` 里边读边写日志 |
| 持久化保证 | ✅ 完全保留原设计（硬杀不丢日志） | ⚠️ 子进程被硬杀时管道内未读数据会丢 —— 这正是当初改成文件背书的原因 |
| 改动面 | `engine/windows.py` 一个文件，约 30 行（`feed()` 抽取 + `tail()`） | `windows.py` + 启动路径 |
| 风险 | tail 线程本身读失败必须不影响任务（try/except 兜住） | 回退了一个已经踩过的坑 |

**选 B1。** 关键实现点：文件读到底返回 0 字节不当作 EOF，`sleep(0.15)` 后继续；进程退出后再多读 ~1.2 s 把尾巴冲干净；`\r` 必须当换行处理（进度条是靠回车重绘的）。

### 4.2 阶段化

sd-cli 在采样前有 20~60 s 的模型加载。现有日志能区分：

| 日志特征 | 映射 stage | 界面文案 |
|---|---|---|
| `| 340/352 - 1.83GB/s`（条尾是**吞吐**） | `loading` | 加载模型 340/352 |
| `|===> | 2/30 - 22.37s/it`（条尾是**每步耗时**） | `sampling` | 采样 2 / 30 · 22.4 s/it · ETA 03:12 |
| 采样后到出图（VAE 解码，约 9 s） | `decoding` | 解码 1.3 s |

**判定不能用「分母 == steps」**（本文 v0.1 写错过，已更正）：图生图时 sd-cli 按
`strength` 反推 `t_enc`，真机日志的分母是 `31 / 108 / 140 / 378 / 426`，而
`--steps` 是 50，一个都不等。可靠判据是**条尾特征的互斥性**——加载条跟吞吐
（`GB/s`），采样条跟每步耗时（`s/it` / `it/s`），两者从不同时出现。

这一段不做的话，用户看到的就是"点了生成 → 黑屏一分钟 → 进度条突然动"。

### 4.2.1 ETA 必须自己算，不能透传 sd-cli 的

sd-cli 打的 `s/it` 是**瞬时值**，但它的 `ETA` 用**累计均值**推算，首帧那一笔把
ETA 抬得离谱。真机三段日志（50 步 / 50 步 / 31 步）对照"真实剩余秒数"：

| 估计来源 | 最大绝对误差 | 中位绝对误差 |
|---|---|---|
| 透传 sd-cli 的 `ETA` | **117 s / 160 s / 354 s** | 3.8 s / 2.3 s / 8.8 s |
| 自己按近 8 步均值算 | **9.9 s / 3.6 s / 4.7 s** | 4.5 s / 2.7 s / 4.0 s |

最大误差全落在**第一步**（首步 `4.54 s/it` vs 其后中位 `1.92 s/it`，冷却/预热差异）。
规则：丢掉第一步，从第 2 笔速率起用近 8 步均值 × 剩余步数；不足 2 笔就不显示
ETA，别猜。按这个规则，剩余 ≥60 s 时相对误差 ≤13%，剩余 <10 s 时相对误差可以
到 33% 但绝对差 <10 s——**验收看绝对差，不看百分比**。

顺带：`total == steps and not throughput` 这条兜底在 7727 行真机 sd-cli 日志里
**一次都没被单独命中**（采样行永远带速率），却能让 ComfyUI 的 tqdm 行
（`0%| | 0/9 [00:00<?, ?it/s]`，分母 4 / 9 / 20）混进采样分支。所以兜底必须
再加一条 `current < total`。

### 4.3 显示

- 细条右边补文字：`采样 12 / 30 · 22.4 s/it · ETA 09:08 · 已用 3:12`
- `total` 未知时不再用 `(0,0)` 静默忙碌态，而是明确写"准备中"
- 完成后在详情里留一行：`生成 337 s（采样 30/30 步）`

### 4.4 队列与"谁占着接口"

多会话同时调用时，现在的界面只会显示"排队中"，不告诉人排第几。需要：

- `X-Client-Id` 头（1–64 字符，`^[A-Za-z0-9._:-]+$`，缺省 `anonymous`）—— **用头而不是共享 token 来区分身份**，因为 token 是所有客户端共用的
- `GET /api/v1/status` → `{active_job, queue_length, position, client_id, stage, elapsed_s}`
- `GET /api/v1/queue` → 前 N 条排队任务的摘要
- 界面：预览卡顶部一条"当前任务"常驻条（与"选中的历史条目"解耦），显示 `谁 · 状态 · 队列位次 · 取消`

这条同时解决 §5 里的"取消按钮跟着选中项走"那个 bug。

## 6. 实施顺序（每批独立可验收、可回滚）

| 批次 | 内容 | 改动面 | 前置 | 验收 |
|---|---|---|---|---|
| **1** | 进度根因（B1 + 4.2 + 4.2.1 + 4.3）+ 顺带修 `GPU_OOM` 判定 | `engine/windows.py`、`engine/sdcpp.py`、`engine/moss.py`、`engine/comfy.py`、`jobs/models.py`、`jobs/scheduler.py`、`desktop` 进度条 | 无 | 真机跑一张 sd-cli 任务（moss 768² 或 Qwen t2i）：加载条不被误判成采样、采样分母与日志一致、解码只给秒数；ETA 在剩余 ≥60 s 时与真实剩余**绝对差 <15 s**；`pytest` 全绿 |
| **2** | 任务详情 A1+A2 + 动作（复用/重跑/复制 JSON） | `desktop` 为主 | 批次 1（阶段文案复用） | 选中历史任一条，字段齐全；复用后左栏与原来一致 |
| **3** | 布局 C1–C10 | `desktop` + `style.py` | 批次 2（同区域改动，合并一次验收） | 1220×840 与 900×680 两种尺寸截图对比 |
| **4** | `/status`（只做这个） | api + jobs + desktop | 批次 2 | 单次轮询拿到"引擎状态 + 当前任务 + 排队数"，桌面端三路 1.1 s 轮询并成一路 |
| **5**（可选） | `engine_parameters` | workflows registry（零迁移） | 批次 2 | 详情里出现步数/CFG/采样器 |

批次 1 必须单独先做：它是引擎层，且 `GPU_OOM` 判定失效是个正确性问题，不只影响观感。

## 7. 验收标准

- `pytest -q` 全绿（当前基线 **106 passed**）
- 新增测试：
  - `feed()` 的 `\r` 分帧、跨块断行、4096 截断
  - `track()` 对 loading / sampling 两类行的判定与 ETA 自算（含"不足 2 笔不显示"）
  - OOM 行 → `gpu_oom=True` → `read_result` 抛 `GPU_OOM`
  - `describe()` 对"缺 `negative_prompt` / 缺 `finished_at` / 有 error"三种老数据的降级
