## 使用约定

**记什么**：任何影响对外接口（REST / MCP / 工作流 / 配置 / 存储 schema / CLI / 打包产物）
或行为语义的改动；纯文档修订也简要记录。

**记在哪**：

- **A 区 · 近期的小功能接口与修改**：参数与字段级调整、错误码增删、小工具脚本、
  文档修正、UI 文案、工作流同版本的尺寸白名单增补、依赖小版本等。**最新条目在顶部，倒序追加。**
- **B 区 · 大功能接口与修改**：新工作流（尤其新 runner/引擎）、REST 契约破坏性变更、
  MCP 工具增删、引擎版本锁定变更、存储 schema 迁移、打包方案变更、安全模型变更。**同样倒序。**
- 判定口径：**需要重新部署 / 需要迁移 / 改变对外契约语义 → B 区**；其余 → A 区。
  一批 A 区小改动累积改变了契约语义时，在 B 区立条目，A 区保留一行指针。

**条目格式**（保持一致，方便日后检索）：

```text
### YYYY-MM-DD · 标题                       ← A 区条目
- 范围: api / engine / workflows / storage / desktop / config / tools / docs
- 变更: 做了什么、为什么
- 接口影响: 无 ｜ <具体变化>
- 验证: pytest ｜ 手工步骤与结果

### YYYY-MM-DD · 标题   [状态: 进行中｜已交付｜已关闭]   ← B 区条目
- 动机:
- 接口影响: REST / MCP / 工作流 / 配置 / 存储 / 打包，逐项列出
- 部署物与迁移: 新增文件、模型、数据目录变化、用户需要的操作
- 验证: 自动化测试 + 实机记录（链接 benchmark.md）
- 遗留: 清单；全部清零后状态改「已关闭」
```

**纪律**：

- 改动完成后**当天**补条目；B 区条目在"遗留"清零前不得标已关闭。
- 每次接口变化时**同步更新 §0 基线**（改动行尾标注日期），基线末尾的"最后核对"日期一并更新。
- 实测数据（耗时、显存、尺寸白名单依据）一律沉淀到 [benchmark.md](benchmark.md)，条目里放链接。

### 0.1 服务与端口

| 服务 | 地址 | 说明 |

### 2026-11-14 · 修复"生到一半卡死"：observe 收尾守卫 advance_ready（两段式回归，moss/qwen 全灭）
- 范围: engine / tests / docs
- 变更:
  - **用户报告**「生图生到一半卡死」。排查：jobs 库无永久卡死任务，但 11-11 上午
    4 单 moss/qwen 全部 `JOB_INTERNAL_ERROR`——两段式改造时 `observe_sdcpp` 无条件调用
    `job.advance_ready(code)`，而 MossJob/KontextJob/QwenImageJob 没有该方法，
    每个 sd-cli 任务收尾必 `AttributeError`（traceback 实锤：comfy.py:361）。
  - **双层根因**：①底层是 moss 大尺寸（1024×768 / 1024²）真 OOM——sd-cli 日志
    `model manager cannot make enough memory available on CUDA0: need 1464.29 MB` +
    `workspace capacity check`（已知 GPU_OOM 措辞，`track()` 本可正确置位）；
    ②回归把 GPU_OOM 吞成笼统 `JOB_INTERNAL_ERROR`；更糟的是 qwen-image-21 1024²
    那单**已解码完成（9/9）**，成品被回归丢弃。
  - 修复：`advance_ready = getattr(job, "advance_ready", None)` 守卫，接续分支仅
    PoseSwapJob 进入；单段 Job 收尾走正常 read_result → GPU_OOM / 成功发布。
- 接口影响: 无（错误码恢复正确语义：GPU_OOM/retryable=true，用户可换小尺寸重试）。
- 验证:
  - pytest **289 通过**。回归锁两把：①真机同款 OOM 行喂 MossJob →
    `observe_sdcpp` 必须抛 GPU_OOM（修复前抛 AttributeError，直接复现事故）；
    ②协议归属——PoseSwapJob 持有 advance/advance_ready，MossJob/KontextJob/
    QwenImageJob 必须不携带。
  - moss OOM 本身是大尺寸 + 显存预算问题（need 1464 MB / available 1343 MB），
    非本缺陷；修复后用户会看到明确的「MOSS-Image 显存不足」并可重试/换小尺寸。
- 部署: dist 重建（00:18）+ verify_packed 全同 + 桌面重启（pid 13112）。
- 遗留: 无。

### 2026-11-11 · 姿势+服装两段式（用户反馈"一起换时姿势跟不上"）+ 分段步数选项

  - **根因（同种子对照实测）**：换装是局部编辑（模型低风险即可满足），换姿势是全局重排

## C · 常用维护操作清单

**新增 / 修订工作流**
1. 建 `workflows/<id>/<semver>/`：manifest.toml + prompt.api.json；对模板算 SHA-256 填 `template_sha256`。
2. `output_node` 必须 SaveImage；inputs 只用白名单键；models 与模板一致；小尺寸先行实机验证，
   `verified_sizes` 只放通过的档位。
3. 补测试（新 runner 必须有）；`pytest -q`；`build-windows.ps1` 重打包；B 区立条目
   （同 workflow_id 新版本自动成为 current，旧版本目录要保留——老任务按原版本执行）。

**修改 REST / MCP 契约**
1. `jobs/models.py`（pydantic）→ `api/app.py` → `mcp/__init__.py` 三处同步。
2. 破坏性变更走 B 区大功能流程，评估 `/api/v1` → `/api/v2`；非破坏性记 A 区。
3. `tests/integration` 补用例；`tools/verify-engine.py` 同步；更新 [项目说明 §3](项目说明.md) 与本文件 §0.1。

**修改配置键**
1. `config.py` Settings（含范围校验）+ `config/default.toml` 同步。
2. 注意 `extra=forbid`：**移除或改名键**会让旧数据目录的 config.toml 启动报错，条目里必须写迁移说明。

**重新打包**
1. `pytest -q` 全绿 → `tools/build-windows.ps1` → 用 dist 包冒烟（`--headless --mock` 或真实引擎）。
2. 核对 `dist\LocalGen\_internal\workflows` 包含全部工作流；dist 作为整体目录分发。

**升级引擎（ComfyUI / sd-cli）**
1. 新版本先隔离验证：独立数据目录 + `--engine-root` 指向新 portable。
2. ComfyUI 版本是源码内硬锁定（`COMFY_VERSION`），升级必须改源码并回归 M1 场景
   （空模型启动、进程树回收、强制退出）。
3. sd-cli 升级需重算并更新 `engine/moss.py` 的 BIN_FILES/MODEL_FILES 钉死值。
4. 更新 §0.5 版本锁定表 + B 区条目。

**引入 Python 依赖**
1. pyproject.toml 精确 pin + requirements-windows.lock.txt 同步；评估 PyInstaller 兼容性
   （uvicorn 相关 hidden-import 已在 build-windows.ps1）。

**备份 / 迁移数据目录**
1. 先正常关闭应用并确认引擎已停；整目录复制；SQLite 运行中备份须用 Backup API。
2. api-token.bin 由 DPAPI 绑定用户，跨 Windows 账户迁移后令牌需重新生成。
